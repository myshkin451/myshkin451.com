实际通过的恢复后检查：

- 使用已有站主密码和通过找回流程设置的访客密码登录目标；两者 UUID 与源环境逐项一致。
- 站主能读取自己的角色，访客不能获得站主身份；访客调用发布 RPC 被拒绝。
- 三种已发布作品均可匿名读取。文章公开正文与草稿不同；站主能读草稿，匿名与访客不能读。
- 留言数量、审核状态、回复的父子关系及删除占位保留；匿名只能读取已审核内容，访客仍可
  查看自己的待审核留言。访客审核留言或编辑站主回复均被服务端拒绝。
- 恢复后没有旧会话和 refresh token；确认、恢复、换邮箱、换手机号及重新认证的旧一次性
  token 字段为空。需要重新登录，而非继承源环境的登录状态。
- 两张已发布图片均可匿名读取，字节长度和 SHA-256 与备份一致：

| --- | ---: | --- |

恢复后、重启前通过 **63 项断言**。随后仅重启恢复目标的全部 7 个容器，包括 PostgreSQL、
Storage、Auth、REST 和网关；等待数据库健康检查恢复后，再次使用已有账号登录，并重复内容、

再向已填充的目标执行同一恢复命令，脚本按设计拒绝；拒绝前后 9 张范围内表的摘要均未变化。
这验证了非空目标保护，没有通过清空数据来让恢复脚本继续。

后续独立审查发现一个导入前保护缺口：如果数据库连接和 API 地址误配到两个不同但均为空的
项目，仅检查两侧空状态不足以证明它们属于同一项目。已交由运维脚本负责人增加临时 nonce
的跨接口读回与清理检查；**该修复及其针对性验证尚未完成，本次成功恢复结果不能替代此项验证。**

演练结束时，源环境的全部 9 张备份范围表摘要仍与备份清单一致。源数据和恢复目标数据均保留；
两个环境仍在运行。没有重置源库、复制测试数据到生产或向云端执行恢复。

## 手工执行迁移后的历史记录

只读检查本地 `supabase_migrations.schema_migrations` 得到：`version text PRIMARY KEY`、
`statements text[] NULL`、`name text NULL`。本地 CLI 记录为版本 `202609210001`、名称
`platform`，并保存了 61 项 statements。

若云端已经通过 SQL Editor 成功执行且核对为同一迁移，可以补记版本，避免 CLI 将其当成
尚未应用的迁移。以下只是准确记录方案，**本演练没有在云端执行这段 SQL**。必须先确认云端
迁移完整、版本尚未误记，不得用它跳过未执行或失败的迁移。

```sql
begin;
create schema if not exists supabase_migrations;
create table if not exists supabase_migrations.schema_migrations (
  version text primary key,
  statements text[],
  name text
);
insert into supabase_migrations.schema_migrations (version, name)
values ('202609210001', 'platform')
on conflict (version) do nothing;
commit;

select version, name, cardinality(statements)
from supabase_migrations.schema_migrations
where version = '202609210001';
```

省略 `statements` 将其留为 NULL，仅登记已应用的版本；不重跑迁移，不伪造 CLI 的逐句记录，
也不覆盖已有记录。未来迁移继续通过迁移工具管理。
